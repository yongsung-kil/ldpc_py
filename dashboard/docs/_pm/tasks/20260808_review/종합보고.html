딥 리뷰 종합 보고 — 상황 설명과 조치 방향

  • 작성: 2026-08-09
  • 대상: 마지막 리뷰(r4, 커밋 ea88882, 2026-08-07) 이후 2_LDPC_light 변경분
  • 근거 문서: r1_round1_lv1_perspectives/ (관점), r2_round2_lv2_analysis/ (분석), r3_round3_lv2_verification/ (검증). 이 문서는 그 결과를 풀어 쓴 요약이며, 수치와 코드 근거의 정본은 각 라운드 보고서다.

1. 한 줄 요약

코드의 골격은 건전하다. 리팩토링은 동작을 그대로 보존했고, 새로 만든 균일 양자화의 저장·로드 왕복도 무손실이며, FER/BER 수치 자체도 정확하다. 문제는 골격이 아니라 그 주변에 있다. ㉮ 저장소에 동봉된 예시 데이터가 기본 설정과 어긋나 있고, ㉯ 균일 양자화 모드의 설계 선택 하나(레벨 0 도입)가 세 가지 증상을 만들고 있으며, ㉰ 파일명과 배치 크기처럼 "결과에 영향 없어야 할 것"이 결과를 바꾸고, ㉱ 문서 여러 곳이 코드의 현재 모습을 따라가지 못했다.

2. 상황 설명

상황 1. 저장소를 받아 그대로 실행하면 FER 1.0이 나온다

지금 config.json은 LLR_MATRIX_HD_1.txt를 가리킨다. 이 파일은 dv=2 구간(변수 노드가 체크 노드 2개에만 연결된 열)의 채널 LLR을 28로 준다. 그런데 3-bit 경로에서 메시지 하나가 낼 수 있는 최대 크기는 7이라, dv=2 열이 받는 반박은 아무리 커도 2×7=14다. 채널이 준 28을 넘어설 수 없으니 이 열의 비트는 어떤 iteration에서도 뒤집히지 않는다. 전체 비트의 11.6%가 이렇게 영구 고정되고, 에러가 조금만 있어도 프레임 전체가 실패해서 FER이 1.0으로 수렴한다.

이것은 디코더 결함이 아니다. 검증에서 디코더 코드를 한 줄도 바꾸지 않고 데이터의 ch만 10으로 낮추자 FER이 정상 범위로 돌아왔다. 알고리즘은 건전하고, 동봉 데이터의 특성이다.

처리 (사용자 확인 2026-08-09): LLR_MATRIX_HD_1.txt는 예시값이며 실사용 대상이 아니다. FER 1.0은 문제가 아니고 별도 조치를 하지 않는다. 실물 H-matrix와 LLR 테이블 반입 시 교체된다 (기존 TODO 항목).

상황 2. 균일 양자화 모드의 "레벨 0"이 세 가지 증상을 만든다

새로 만든 균일 n-bit 양자화는 메시지 크기 레벨을 [최대값..0]으로 잡았다. 원본 C++ 하드웨어는 내부 상태로는 0을 쓰지만 체크 노드가 내보내는 메시지는 최소 1로 되돌린다. 즉 원본에는 "크기 0인 메시지"가 존재하지 않는데, Python 균일 모드에만 생겼다. 여기서 세 증상이 나온다.

  • ㉮ 공명 붕괴: 채널 LLR이 특정 값(이 부호에서는 top_level과 같은 값, 예로 6-bit이면 31)일 때 iteration 1에서 합이 정확히 0이 되는 공명이 일어나고, 그 0이 레벨 0으로 살아남아 체크 노드를 침묵시킨다. FER이 1.0으로 붕괴하는데 경고 한 줄 없이 완주한다. 인접한 ch 값(30, 32)은 멀쩡해서, 파라미터 스윕을 하다가 특정 지점만 이상하게 나빠 보이는 함정이 된다.
  • ㉯ min1 점유: 크기 0인 메시지는 항상 최솟값 자리를 차지해서 그 체크 노드가 한 엣지만 빼고 전부 0을 내보내고, 정작 그 한 엣지는 근거 없는 최대 확신값을 받는다. 워터폴 구간에서 FER을 1.2~1.9배 나쁘게 만드는 것이 실측됐다.
  • ㉰ CSW 로그 오염: 크기 0에 음수 부호가 붙으면 부동소수점 -0.0이 되는데, 현재 부호 판정이 이를 양수로 읽어 부호가 사라진다. 복호 결과(FER/BER)는 기본 설정에서 영향이 없지만, 지금 켜져 있는 csw_mean과 final_csw 로그는 전 행이 틀린 값으로 저장되고 있다. CSW 곡선을 보고 아이디어의 수렴을 판단하면 틀린 근거로 판단하게 된다.

세 증상의 뿌리가 하나이므로 수리도 하나로 가능하다. 균일 레벨의 최소를 1로 바꾸면(구체안: edge_mag를 [top..2,1,1]로) 세 증상이 동시에 사라지는 것이 검증에서 실측됐고, 파일 포맷과 이미 커밋된 매트릭스 파일도 그대로 유효하다. 다만 이것은 동작 변경이므로 사용자 결정이 필요하다(4절 결정 1).

[top..2,1,1]의 뜻과 C++ 대응 (사용자 질문 2026-08-09에 대한 답)

  • ㉮ th(비교 임계값) 목록은 지금처럼 [top..1] (top개)로 두고, VNU 출력 레벨 목록(edge_mag)만 바꾼다. 현재 [top, ..., 2, 1, 0]의 마지막 0을 1로 치환해 [top, ..., 2, 1, 1] (top+1개)로 만드는 안이다. 레벨 개수가 th 개수+1이어야 한다는 로더 제약 때문에 항목 수를 유지한 채 0 자리만 1이 된다. 동작은 크기 = max(min(|raw|, top), 1), 곧 크기 0이 나올 자리에 1이 나온다
  • ㉯ C++도 메시지 크기 0을 내보내지 않는다. 3-bit 레벨은 {7,5,3,1}로 0이 없고, 내부 압축 도메인의 0(V_VERY_WEAK)은 C2V 변환에서 최소 1(EDGE_MAG_1)로 복원된다 (decoder.cpp:2405, common.h:338-341). 4-bit 빌드도 같다. "메시지 크기 0 금지"는 C++와 같은 방향이다
  • ㉰ 다만 C++ 4-bit의 숫자 매핑을 문자 그대로 옮기면 레벨이 [top+1..1] (크기 = min(|raw|, top) + 1)이 되어 ㉮와 크기가 1씩 다르다. ㉮는 상한 top을 유지하고 하한만 1로 막는 포화형이다. 둘 중 무엇을 균일 n-bit의 정의로 삼을지가 결정 1의 선택지다 (㉮ 권고안은 FER 개선까지 실측 완료, C++ 그대로 안은 별도 측정 필요)

상황 3. 파일명이 디코딩 의미를 결정한다

LLR matrix 파일에는 채널 LLR과 th(비교 임계값)만 저장되고, VNU 출력 레벨 목록(edge_mag: 양자화 결과로 나올 수 있는 크기들)은 저장되지 않는다. 그래서 load()는 레벨 목록을 파일 밖의 정보로 정해야 하는데, 현재 그 정보가 파일명이다.

  • ㉮ 파일명에 uniform 문자열이 있으면: 균일 생성물로 간주하고 th 개수 n에서 레벨 [n..0]을 재구성한다
  • ㉯ 없으면: 사람이 만든 파일로 간주하고 고정 레벨 {7,5,3,1}을 쓴다 (th가 3개가 아니면 에러)

같은 내용의 파일이라도 이름에 따라 다른 레벨로 복호된다는 뜻이다. 문제가 되는 지점은 두 가지다.

  • ㉮ 판정이 "부분문자열 포함" 검사라 오탐한다. 예로 nonuniform이 든 이름도 uniform 포함으로 걸린다. 사람이 만든 3-bit 파일을 그런 이름으로 두면 레벨이 {7,5,3,1}이 아니라 [3,2,1,0]으로 잡힌다
  • ㉯ 어느 방향으로 어긋나도 에러와 경고가 없다. 끝까지 돌아 FER을 보고하므로 사용자는 알 수 없다. 실측으로 같은 파일을 이름만 바꿔 로드하니 FER이 0.8906 대 0.9688로 갈렸다

수리 방향은 판정 근거를 파일명에서 파일 내용으로 옮기는 것이다. "th 값이 [n..1] 연속 정수 내림차순이면 균일 생성물"이라는 값 기반 판정식이 검증에서 확인됐다 (내부 생성물에 참, 사람이 만든 DAO 3-bit 파일에 거짓, restart 행의 th=-1도 자동으로 걸러진다).

상황 4. 배치 크기가 결과를 바꾼다

문서 세 곳이 "frames_per_batch는 결과에 영향 없음"이라고 단언하지만, 실측으로 같은 seed에서 FER이 달라진다(0.3867 대 0.3750). 원인은 두 겹이다.

  • ㉮ 배치마다 메시지 난수를 뽑아 버리는 호출이 있어서 배치 경계가 바뀌면 잡음 난수의 위치가 밀린다. 프레임마다 난수 스트림을 따로 파생시키면 해결되고 비용 증가는 없다.
  • ㉯ 난수를 완전히 정렬해도, 조기 종료 규칙(max_frame_errors)이 배치 단위로 검사되어 종료 프레임 수가 배치 크기의 배수로 양자화된다. 이것은 난수와 별개의 문제라 별도 결정이 필요하다.

재판정 (사용자 지적 2026-08-09 반영): 통계 관점의 지적이 맞다. 두 실행 모두 편향 없는 표본이라 프레임 수가 충분하면 같은 FER로 수렴하며, 통계적 결론을 바꾸는 결함이 아니다. 아이디어 A/B 비교도 같은 config(같은 배치 크기)로 돌리는 한 영향이 없다. 남는 조치는 문서 문언 교정뿐이다. "결과 영향 없음" 단언 3곳을 "통계 결과는 프레임 수가 충분하면 같고, 같은 seed의 수치 재현에는 배치 크기까지 같아야 한다"는 취지로 바꾼다. 코드 수리(프레임 단위 난수 파생, 종료 규칙 변경)는 하지 않는다.

상황 5. 새 환경의 첫 실행에서 summary.txt가 사라진다

그림 저장이 summary.txt 저장보다 먼저 실행되는데, matplotlib이 없으면 그림 저장에서 죽는다. 측정은 다 끝난 뒤라 CSV는 남지만, 커밋 해시와 "실제로 어떤 디코더 클래스가 쓰였는지"의 기록은 summary.txt에만 있어서 함께 사라진다. 저장소에 의존성 선언 파일(requirements 등)이 하나도 없고 두 config 모두 그림 저장이 기본 켜짐이라, 외부에서 pull한 첫 실행이 정확히 이 경로를 탄다. 저장 순서 교체와 try/except 병용으로 바로 고칠 수 있다.

상황 6. 문서가 코드를 따라가지 못했다

균일 n-bit 모드가 들어왔는데 README와 차이.md에 "3-bit 전용, 레벨 {7,5,3,1} 고정"이라는 옛 서술이 남아 있다(32레벨 복호가 실제로 성공하므로 명백히 거짓). "use_input_llr_matrix가 false면 llr_matrix 키는 무시된다"는 서술도 거짓이다(dir 하위 키가 생성 위치로 실제 사용됨). 실행 안내 두 곳이 이제 존재하지 않는 _test/ 경로를 실험 루트로 지목해서 따라 하면 import 에러가 난다. encoder.py의 "실물 인코더가 필요하면 이 함수만 채우면 된다"는 서술도 거짓이다(정답 코드워드가 디코더에 all-zero로 하드코딩되어 있어 파급이 크다).

처리 (사용자 확인 2026-08-09): 지금 수정 가능한 것은 바로 수리한다. README를 코드 변경마다 항상 최신으로 유지하는 의무는 두지 않는다.

상황 7. 정리 작업의 잔재 두 건

  • ㉮ 구 코드 삭제 커밋(2e600ea)이 llr_tables.py 하나를 빠뜨렸다. import하는 곳이 없는 사문 모듈이다
  • ㉯ 구 examples/llr_tune.py가 담당하던 "여러 LLR 후보를 같은 조건으로 돌려 FER 표로 견주는" 절차는 삭제됐고 이 저장소 안에 대체가 없다

처리 (사용자 확인 2026-08-09): 둘 다 버린다. llr_tables.py는 삭제한다 (주석의 구 하드웨어 CH_HD 값 {21,14,12,10}은 보존하지 않는다). llr_tune의 탐색 절차는 되살리지 않고 TODO에도 올리지 않는다. 나중에 필요해지면 그때 구현한다.

참고. 균일 모드는 dv별 ch 차등을 표현하지 못한다 (문제가 아니라 특성)

균일 모드는 모든 dv 구간에 채널 LLR 하나를 공통으로 준다. 실사용에서는 dv별로 ch를 다르게 줄 것이므로, dv 차등이 필요한 실험은 LLR matrix 파일 경로로 하면 되고 그 경로는 dv별 ch를 이미 지원한다. 검증 재실험에서도 dv별 차등이 공통 ch보다 FER을 크게 개선할 수 있음이 확인됐다 (같은 채널에서 9.3배). 동봉 예시 파일과의 비율 비교 서술은 그 파일이 예시값이라 의미가 없으므로 판단 근거에서 뺐다 (사용자 확인 2026-08-09).
