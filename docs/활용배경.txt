AI-Dev-Assistant 활용 배경

[출발점]

코드가 있는 프로젝트를 오래 맡으면 코드 밖에 쌓이는 것이 더 많아진다. 읽어야 할 논문, 시도했다가 접은 아이디어, 그때그때 내린 결정, 손으로 돌리던 최적화 실험, 누구에게 물어야 아는 실행 방법. Claude 같은 도구를 붙여도 대화가 끝나면 이 맥락이 사라지고, 다음 대화는 코드를 처음부터 다시 읽는 데서 시작한다. 이 플러그인은 그 반복을 없애려고 만들었다. 한 문장으로 말하면 "코드 밖의 지식을 코드 옆에 파일로 쌓고, Claude가 매번 그 파일부터 읽게 하는 것"이다.

[필요와 구성 요소의 대응]

- 매번 코드를 처음부터 읽는 문제 -> 온보딩(프로파일)
  프로젝트가 무엇이고(개요), 어떻게 짜였고(구조), 어디에 새 기법을 끼우며(교체 지점), 이미 무엇을 갖고 있고(보유 기법), 무엇을 바꾸면 안 되는지(제약)를 다섯 문서로 고정한다. 모든 스킬이 코드 대신 이 문서를 먼저 읽는다. 사용법 문서는 새로 온 사람과 쓰는 법을 잊은 사람이 맨 먼저 여는 한 장이다.

- 대화가 끝나면 사라지는 진행 상황 -> 작업 관리
  할 일, 끝낸 일, 작업별 설계 문서, 그리고 사람만 정할 수 있는 것을 모아 묻는 판정요청을 _pm/ 폴더에 둔다. 세션을 열면 할 일 요약이 자동으로 들어오므로 어제 어디까지 했는지 다시 설명하지 않는다.

- 현황을 알려면 폴더를 뒤져야 하는 문제 -> 대시보드
  작업 보드(계획, 진행 중, 완료), 변경 이력, 문서 지도를 정적 html 한 벌로 만든다. 서버 없이 파일만 열어도 되고 GitHub Pages에 그대로 올라간다. 회의 전에 "지금 어디까지 왔나"를 한 화면에서 본다.

- 논문과 특허가 쌓이기만 하는 문제 -> 외부 기술문서
  수집(arXiv, IEEE, 특허), 초록 선별, 전문 분석을 정해진 기준서로 돌리고 결과를 DB 하나에 모은다. 탐색기 페이지에서 검색어, 연도, 이식성이나 추천도 같은 갈래로 거른다. 읽은 논문이 "누가 어디에 저장했는지 모르는 PDF"가 아니라 검색되는 자료가 된다.

- 논문의 기법을 코드에 붙여 보는 일이 사람마다 제각각인 문제 -> 아이디어 적용
  프로파일의 교체 지점에 기법을 끼우고, 기준 실험과 같은 조건으로 비교하고, 결과를 실험 로그와 현황표에 남긴다. 접은 아이디어도 "왜 접었는지"가 남는다.

- 최적화가 개인의 손과 감에 기대는 문제 -> 최적화
  결과를 바꾸지 않는 속도 개선은 점검표를 한 항목씩 밟으며 동일성 근거를 남기고, 안정성 검사는 재현부터 회귀 테스트까지 정해진 순서로 한다. 파라미터 최적화는 평가 명령과 파라미터 범위만 적으면 도구가 탐색하도록, 도구를 만드는 순서까지 안내한다. 사람은 무엇을 좋게 할지와 무엇을 바꿀지만 정한다.

- 얻은 지식이 한 사람의 머리에만 있는 문제 -> 내부 기술문서(위키)
  대화, 커밋, 완료 작업에서 결정(왜 그렇게 정했나), 시도(해 봤지만 접은 것), 재사용 패턴, 코드 동작 설명을 뽑아 쌓는다. 바깥 문헌은 외부 기술문서에, 프로젝트 안에서 나온 것은 여기에 둔다는 한 가지 기준으로 나눈다.

- 계획, 리뷰, 디버그, 테스트 설계를 매번 즉흥으로 하는 문제 -> 절차 스킬
  작업자 여럿이 관점을 나눠 맡고 교차 검증하는 절차를 스킬로 고정해, 사람이 매번 지시문을 다시 쓰지 않는다.

[전제]

- 언어와 분야를 가리지 않는다. 프로파일이 언어와 무관한 낱말(모듈, 인터페이스, 교체 지점, 신호)로 적히므로 C++, Python, Verilog 프로젝트에 같은 절차가 돈다.
- 설치할 것이 없다. 스크립트는 Python 표준 라이브러리만 쓰고, html은 정적 파일이라 인터넷이 막힌 자리에서도 열린다.
- 결과물은 전부 저장소 안의 md와 html이다. 도구를 걷어내도 문서는 남는다.
