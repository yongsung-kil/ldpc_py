## 1. F8 검증

### 1-1. ㉮ C++ 두 캐스케이드 블록과 바깥 조건: 확인됨

`VN_Cal_HD`(`0_LDPC_original/decoder.cpp:3973`) 안에 캐스케이드 블록이 두 개 있고, **바깥 조건은 두 단계**다.

**바깥 1단계 (BF 대 비BF)**: `decoder.cpp:4055-4059`

```c
#ifdef __AUTO_LLR_OPT__
    if ((TRUE == flag_BF_on) && (iter <= 4) && (v_deg > DV_5)) { //1bit precision
#else
    if ((TRUE == flag_BF_on) && (iter <= ITER_MAX_HBF) && (v_deg > DV_5)) { //1bit precision
#endif
```

- ㉮ `DV_5 = 5` (`common.h:295`)
- ㉯ AUTO 빌드에서 `Select_BF()`가 `flag_BF_on = FLAG_LOW`를 무조건 대입한다 (`decoder.cpp:2083-2085`, `#if defined (__AUTO_LLR_OPT__)` 분기). 초기화도 `FLAG_LOW`다 (`decoder.cpp:609`)
- ㉰ 따라서 AUTO 빌드에서는 **항상 `else` 쪽(`decoder.cpp:4080`, 주석 `// 4bit precision`)으로 들어간다**. Python이 BF 구간을 재현하지 않는 것은 이 전제와 맞다

**바깥 2단계 (문제의 두 블록을 가르는 조건)**: `decoder.cpp:4082` `if (temp_m == 0)`

즉 **`raw == 0` 여부**다 (BF 구간 여부가 아니다). `temp_m`은 `decoder.cpp:4052-4053`에서 `temp = sum_t - VNU_in[mux_idx][j]; temp_m = abs(temp);`로 만들어진다.

| 블록 | 위치 | 조건 | 캐스케이드 본문 | 부호 결정 |
|------|------|------|----------------|----------|
| zero 분기 | `decoder.cpp:4092-4096` (`#else`, 3-bit) | `temp_m == 0` (`4082`) | `>=th1→7, >=th2→5, >=th3→3, else 1` | `VNU_in > 0 ? +mag : -mag` (`4098-4099`) |
| non-zero 분기 | `decoder.cpp:4111-4115` (`#else`, 3-bit) | 위의 else (`4101`) | **완전히 동일한 본문** | `temp > 0 ? +mag : -mag` (`4117-4118`) |

- ㉮ `__4_BIT_LLR__`는 `mode.h:12`에서 주석 처리되어 있으므로 8레벨 블록(`4084-4091`, `4103-4110`)은 컴파일되지 않는다. `#else` 3-bit 블록만 유효하다
- ㉯ `EDGE_MAG_7/5/3/1 = 7/5/3/1` (`common.h:342-345`, `#else` 3-bit 절)
- ㉰ **두 블록의 캐스케이드 본문이 글자 그대로 같다.** 다른 것은 부호 출처뿐이다

**Python 대응 검증 (`decoder.py:76-102`)**: **확인됨**

- ㉮ Python은 캐스케이드(magnitude)를 조건 없이 한 번만 계산하고(`decoder.py:93-96`), 부호만 `zero` 마스크로 갈라 끼운다(`decoder.py:97-101`). C++ 두 블록의 본문이 동일하므로 이 인수분해는 **등가**다
- ㉯ 경계 취급도 일치한다. C++ `if (VNU_in > 0) + else -`이므로 `VNU_in == 0`은 음수, Python `np.where(c2v > 0, +1, -1)`도 `c2v == 0`에서 음수다 (`decoder.py:100`)
- ㉰ non-zero 분기의 `temp`는 정의상 0이 아니므로 `temp > 0` 대 `raw > 0`(`decoder.py:97`)은 등가다
- ㉱ 즉 **`zero` 분기 대응 자체는 문제가 없다**. F8의 결함은 오직 캐스케이드를 지시함수 합으로 바꾼 데 있다

`_vnu_quantize`(`decoder.py:72-88`)도 같은 구조이며, **같은 결함을 갖는다** (`decoder.py:81`). 다만 이쪽의 BF 분기(`decoder.py:77`)는 C++의 `flag_BF_on` 항을 빼고 있어 AUTO 전제와 어긋나는 별건이 있다 (F8 범위 밖, 참고용 기재).

## 2. F14 검증

### 2-1. ㉮ C++ `VN_Cal_HD`의 `sum_t <= 0` 동점 반전: 확인됨

원문 (`0_LDPC_original/decoder.cpp:4043-4045`):

```c
        /* syndrome-aided decoding */
        if (sum_t > 0)  cwc[bit_pos] = Variable_mem[bit_pos];
        else            cwc[bit_pos] = (Variable_mem[bit_pos] + 1) % 2;
```

`sum_t == 0`은 else로 떨어지므로 **동점은 반전**이다. Python `decoder.py:398` `flip = total <= 0`과 등호 위치까지 같다.

VN 판정 함수 **전수 확인** (`grep -n "sum_t *[<>=!]" decoder.cpp`):

| 함수 | 판정 위치 | 조건 |
|------|----------|------|
| `VN_Cal_HD` | `decoder.cpp:4044` | `sum_t > 0` |
| `VN_Cal_HD_HCU` | `decoder.cpp:4253` | `sum_t > 0` |
| `VN_Cal_CD` | `decoder.cpp:4431` | `sum_t > 0` |
| `VN_Cal_SD` | `decoder.cpp:4577` | `sum_t > 0` |
| `VN_Cal_SD_HCU` | `decoder.cpp:4768` | `sum_t > 0` |

`sum_t >= 0` 형태는 **한 곳도 없다**. `1_LDPC_revised/decoder.cpp`도 5곳 모두 `sum_t > 0`으로 동일하다 (`4105`, `4287`, `4446`, `4581`, `4761`).

### 2-2. ㉯ signed 도메인에 C++ 대응 원문이 있는가: 확인됨 (존재하지 않는다, V1 주장이 맞다)

- ㉮ 다섯 VN 함수 모두 `sum_t`를 `channel_llr`로 초기화한다 (`decoder.cpp:4026`, `4215`, `4413`, `4566`, `4739`). `channel_llr`은 테이블값 `ch1` 또는 `CH_LLR_MAX`/`CH_LLR_MIN`이며 **read bit의 부호가 실리지 않는다** (`decoder.cpp:4017-4024`)
- ㉯ read bit `Variable_mem`은 판정식의 **오른쪽**(`cwc` 대입)에만 나타난다 (`decoder.cpp:4044-4045`). 즉 `sum_t`는 항상 "현재 read bit 기준 상대값"인 flip 도메인이다
- ㉰ 따라서 C++ 원본 전체에 **signed LLR 도메인의 VN 합 판정이 존재하지 않는다**. `two_set`(`decoder.py:170`)과 `column_wise`(`decoder.py:268`)는 대조할 원문이 없는 자체 구현이다

**V1의 "각자 도메인에 맞음" 주장은 확인됨.** V4의 "matrix는 동점을 오류로 세고 signed는 정답으로 센다"는 서술도 사실이지만, 그것이 곧 "signed 쪽이 원문에서 벗어났다"를 뜻하지는 않는다.

추가로 짚을 비대칭이 하나 있다.

- ㉮ **flip 도메인의 동점은 all-zero 전제와 무관하다.** `total <= 0`이면 read bit을 뒤집는다는 뜻이므로, 그 결과가 정답인지는 read bit이 무엇이었는지에 달린다. 송신 codeword가 무엇이든 규칙 자체가 대칭이다
- ㉯ **signed 도메인의 동점은 all-zero 전제 때문에 한쪽으로 쏠린다.** `total < 0`을 "비트 1 = 에러"로 보는 규칙은 그 자체로 편향이 아니지만, `encoder.encode()`가 항상 all-zero를 돌려주므로(`encoder.py:16-19`) 동점이 **언제나** 정답으로 집계된다
- ㉰ 즉 두 경로의 동점 문제는 **뿌리가 다르다**. 같은 규칙을 강제할 근거가 되지 않는다

## 판정

### F8 판정: **갈래 2 (캐스케이드로 교체)**. 단 `np.select`가 아니라 **중첩 `np.where`**

근거:

- ㉮ **갈래 1은 프로젝트 목표를 해친다.** C++는 th 정렬을 어디에서도 검사하지 않고(1-4), 비단조 th를 받아 캐스케이드 의미로 소비한다. `_validate()`에서 거부하면 **C++이 정상 처리하는 파일을 Python이 거부**하게 되어, 루트 `CLAUDE.md` "프로젝트 간 흐름 ㉰"(외부의 H-matrix와 파라미터를 넣어도 동작하는 것이 목표)를 정면으로 위반한다
- ㉯ **갈래 2는 원문 등가다.** C++ 캐스케이드와 중첩 `np.where`는 조건 순서와 등호 위치가 1대1로 대응한다. 스칼라 캐스케이드 레퍼런스 대조에서 내림차순 th와 비단조 th 양쪽 모두 불일치 0건이다 (1-6). 현행 입력에서 `success`/`n_iter`가 완전히 일치하므로 회귀도 없다
- ㉰ **성능 비용이 없다. 오히려 이득이다.** 호출당 0.503배, 전체 실행 9.1% 단축 (1-6). `np.select`는 1.339배로 느려지므로 처방 원문의 "`np.select`"는 **중첩 `np.where`로 바꾸는 것을 권고**한다
- ㉱ 방치 시 위험은 실측으로 확인되었다. 비단조 th에서 v2c의 14.5% ~ 56.2%가 달라지고 n_iter가 최대 15/32 프레임에서 갈리는데 **에러도 경고도 나지 않는다** (1-3)

적용 범위:

- ㉮ `_mx_vnu_quantize`(`decoder.py:93-96`)를 중첩 `np.where` 캐스케이드로 교체
- ㉯ `_vnu_quantize`(`decoder.py:81`)도 **같은 결함이므로 함께 교체**한다. 이 경로가 존치될 경우에 한한다 (F23 존치 여부 Decision과 묶인다)

### F14 판정: **갈래 1 (현행 유지 + 문서화)**. 갈래 2는 반대

V1과 V4는 **양립 가능하다**. "정확성 문제 아님(V1)"과 "경로 간 비교 시 계통 오차 주의를 문서화(V4)"가 동시에 성립한다. 근거:

- ㉮ **V1이 옳다.** C++에는 signed 도메인 VN 판정이 존재하지 않는다 (2-2). matrix 경로의 `<=`는 원문 강제 사항이고(`decoder.cpp:4044`, 다섯 함수 전부), signed 두 경로는 대조할 원문이 없다. 따라서 "matrix와 다르다"는 사실은 결함의 근거가 되지 못한다
- ㉯ **갈래 2는 문제를 해결하지 못한다.** 무작위 tie-break 기준선이 `<`(0.1458)와 `<=`(0.1562) 사이인 0.1536이다 (2-4). `<=`로 바꾸면 낙관 편향이 **같은 크기의 비관 편향**으로 바뀔 뿐이다. "matrix와 형태가 같아 보인다"는 것 말고는 얻는 것이 없고, 오히려 "이제 세 경로가 통일되었다"는 잘못된 안심을 준다
- ㉰ **두 동점의 뿌리가 다르다** (2-2 말미). flip 도메인의 동점은 송신 codeword와 무관한 대칭 규칙이고, signed 도메인의 동점 쏠림은 `encoder.encode()`가 all-zero만 돌려주는 데서(`encoder.py:16-19`) 온다. 규칙을 맞추는 것은 증상 대칭일 뿐 원인 대칭이 아니다
