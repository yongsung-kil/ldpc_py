## 물음 1. 이 사본에서 변형 디코더 실험을 돌릴 수 있게 실험 폴더의 실행 파일(run.py)을 고칠지 정한다

변형 디코더는 기본 디코더 클래스(BaseDecoder)를 상속해 계산 단계 일부만 바꿔 끼운 자식 클래스다. 실험 폴더는 `workspace/` 아래 다섯 개(`_template`, `base_run`, `test`, `matrix_sel_1_HD`, `matrix_sel_1_HD_fixed`)이고, 각 폴더의 `run.py`(런처: 설정 파일을 읽어 본체 코드를 부르는 짧은 파이썬 파일)는 내용이 같다.

- 🔎 예시: 2026-09-30 02:55, `workspace/test/` 폴더에서 `python run.py`를 실행했다
  - 실행 파일이 조상 폴더(위로 올라가며 만나는 상위 폴더들)를 차례로 보며 `2_LDPC_base/src` 폴더를 찾는다 (`workspace/test/run.py:12`)
  - 이 저장소의 폴더 이름은 `ldpc_py`라 어느 조상 폴더에도 그 폴더가 없다
  - 화면에 이 글이 나오고 끝난다: `상위 폴더에서 2_LDPC_base/src를 찾지 못함 (이 파일은 LDPC_dev 하위 실험 폴더에 있어야 함)`
  - 같은 날 03:01, 저장소 루트에서 `python -m src.run <설정 파일>`로 돌리면 정상 동작한다 (32프레임, 약 2.7초. 프레임은 부호 블록 하나를 보내고 복호하는 단위다). 그러나 이 명령은 기본 디코더만 쓴다. 변형 디코더를 받을 자리가 없다 (`src/run.py:794-795`)
  - 1️⃣ 이면: 다섯 `run.py`의 12행 조건에 "이 저장소의 `src/run.py`가 있는 조상 폴더"도 허용하도록 한 줄을 더한다. `python run.py`가 이 사본에서도 원본 배치(원래 폴더 구조 `LDPC_dev/2_LDPC_base`)에서도 동작한다. 변형 디코더는 `run.py` 안의 `DECODER_CLASS` 변수(어느 디코더 클래스를 쓸지 적는 자리)에 이름을 적어 넣는다
  - 2️⃣ 이면: 기존 `run.py`는 그대로 둔다. 저장소 루트를 찾아 넣는 새 실행 파일 하나(예: `workspace/run_local.py`)를 더한다. 변형 실험은 `python ../run_local.py config.json`처럼 새 파일로 돌린다. 원본 배치에는 이 새 파일이 없어 실험 폴더마다 실행 명령이 원본과 달라진다
  - 3️⃣ 이면: 아무것도 바꾸지 않는다. 이 사본에서는 기본 디코더 실험만 `python -m src.run`으로 돌린다. 변형 디코더 실험은 원본 배치에서만 한다
- 📌 상황: 런처는 본체 코드의 위치를 폴더 이름 `2_LDPC_base`로 찾는다. 원본 배치에는 `LDPC_dev/2_LDPC_base/`가 있어 찾는다. 이 사본은 폴더 이름이 `ldpc_py`라 찾지 못한다. 지금은 아무것도 고치지 않았다
- ⚠️ 문제: 이 사본에서는 변형 디코더를 실행할 길이 없다. 그래서 새 기법을 붙이는 절차(양식 복사, 재정의 코드 쓰기, 실행해서 기준 실험과 비교)가 "실행" 단계에서 막힌다
- ❓ 결정할 것
  - 1️⃣ (권고) 다섯 `run.py`의 탐색 조건에 한 줄을 더한다. 고칠 범위는 파일 5개의 12행 근처 3줄씩. git으로 되돌리기 쉽다. 원본 배치로 다시 복사해도 동작이 같다
  - 2️⃣ 새 실행 파일 하나를 더한다. 기존 파일은 손대지 않는다. 대신 실험 폴더마다 실행 명령이 원본과 달라진다
  - 3️⃣ 바꾸지 않는다. 고칠 범위 0. 변형 실험은 원본 배치에서만
  - 권고 까닭: 원본과 사본 양쪽에서 같은 명령 `python run.py`가 통한다. 기존 README와 설정 파일(config.json)의 "실행: 이 폴더에서 python run.py" 설명도 고칠 필요가 없다
  - 권고가 맞지 않는 경우: 이 사본을 원본과 한 글자도 다르지 않게 유지해야 한다면 3️⃣

## 물음 3. 입력 파일의 출처와 실값을 문서에 적지 않는 규칙을 새로 둘지 정한다

입력 파일은 두 종류다. H-matrix는 부호의 검사 행렬 파일이고, LLR 테이블은 수신 비트에 줄 확신도 값(LLR)을 iteration과 비트 종류별로 적은 표 파일이다. 프로파일은 다른 자동 작업이 이 저장소를 건드리기 전에 읽는 안내 문서 묶음(`docs/profile/` 다섯 문서)이다. 이력물은 끝난 작업의 기록 문서다.

- 🔎 예시: `README.md` 223행에 이렇게 적혀 있다: `LLR 값은 원본 소스 손상으로 소실되어 사용자가 Input/에 넣는다`
  - `_pm/TODO.md` 31행: `벤더 참고값: dv=2 ch=10` (벤더는 공급자. dv는 한 비트가 연결된 검사식 수, ch는 그 비트에 줄 채널 LLR 크기. 2와 10이 공급자가 준 값)
  - `_pm/done/20260806_review/r3_round3_lv2_verification/worker_b_1.md` 146~163행: 공급자의 3비트 채널 테이블(수신값을 3비트 8단계로 나눈 채널의 LLR 표) 실값 네 개가 표로 실려 있다
  - 프로파일 양식 `docs/profile/constraints.md` 2절은 "문서와 로그에 적으면 안 되는 것 (예: 입력 파일의 출처와 성격)"을 적는 자리다. 이 저장소에는 그런 규칙이 글로 없다
  - 1️⃣ 이면: 규칙을 새로 만들지 않는다. 2절에는 "평가 대상 입력 파일 자체를 저장소에 넣지 않는다"(README.md:223, 이미 있는 결정)만 적는다. 출처 표기 규칙은 "없음(미확인)"으로 둔다. 위 세 곳의 글은 그대로다
  - 2️⃣ 이면: "입력 파일의 공급자 이름과 공급자가 준 실값을 문서에 적지 않는다"를 규칙으로 2절에 올린다. 문구 5곳을 고친다. 예: (지금) `벤더 참고값: dv=2 ch=10` → (바꾼 글) `참고값: 공급자 자료 참조`. 5곳은 `README.md:223`, `_pm/TODO.md:31`, `_pm/DONE.md:369`, `_pm/done/20260806_review/r3_round3_lv2_verification/worker_b_1.md:146-163`, `_pm/done/20260809_2SD3SD구현/cpp_sd_analysis.md:313-321`이다. 이 중 뒤 셋은 이력물이라 물음 2와 같은 충돌이 생긴다
- 📌 상황: 이 저장소는 외부 시뮬레이터(Ref-C: 원본 C++ 시뮬레이터)와 외부 도구(DAO: LLR 테이블 최적화 도구)의 이름을 코드 주석과 README 전반에서 쓴다. 그 이름 자체는 코드를 읽는 데 필요하다. 문제가 되는 것은 공급자와 그 실값을 가리키는 문구다. 지금 규칙은 없다. 문구도 그대로다
- ⚠️ 문제: 규칙 없이 두면 프로파일 2절이 비어 다른 스킬(이 저장소에서 돌아가는 자동 작업 절차)이 무엇을 피해야 하는지 모른다. 규칙을 두면 이력물까지 고쳐야 한다
- ❓ 결정할 것
  - 1️⃣ (권고) 규칙을 새로 만들지 않고 "없음(미확인)"으로 적는다. 고칠 범위는 프로파일 2절 한 줄(이미 있는 결정을 옮겨 적음). 본문 문서는 0
  - 2️⃣ 규칙을 올리고 문구 5곳을 고친다. 고칠 범위는 파일 5개. 이력물 3개 포함 (`_pm/DONE.md`, `worker_b_1.md`, `cpp_sd_analysis.md`). 물음 2에서 2️⃣(이력물 그대로)를 골랐으면 이력물 3개는 빼고 나머지 2개만 고친다
  - 권고 까닭: 프로파일은 확인된 규칙만 적는 문서다. 없는 규칙을 지어 넣는 것보다 사용자가 정한 뒤 적는 것이 맞다
  - 권고가 맞지 않는 경우: 이 저장소를 밖에 공개할 계획이 있다면 2️⃣
